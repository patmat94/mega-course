Three wake triggers, or one shared subscribe/wake primitive?

rig-pulse, mail-agent and away-agent are each woken by an outside service: a signed HTTPS call arrives, the Worker must check it, answer fast and then do the work. Today each one does this its own way. This page compares keeping them separate with building one shared primitive.

Decision: build it as a small module, not as a shared service

Worth building: one module of roughly 120 lines, taken from mail-agent's queue path: verify → dedupe → enqueue → 2xx, then a queue consumer that runs the handler and sends each outbound push with retries until a 2xx.

  • It fixes the one failure that repeats across lessons: work done in ctx.waitUntil that dies without a trace. That is how away-agent lost its ping in try 6, and rig-pulse uses the same pattern. A queue keeps the job pending and retries it, which is what ADR 0008 asks for.
  • Do not build a hosted wake service that the three Workers subscribe to. It would hold three course signing keys in one place, put a single point of failure in front of Workers the course still calls, and cut across the rule that running Workers stay as they are unless you say otherwise.
  • Use it first for the next Worker a lesson needs. Move away-agent onto it only if it has to answer the course again. Leave rig-pulse alone: its may lists must stay exact, and it gains the least.
  • What it does not fix: ntfy.sh being unreachable from Cloudflare (429, then 522 for about 12 minutes). A retry keeps the ping alive but it still arrives late. That needs a second push channel, which is a separate decision.

The module's shape

fetch(req) verify(adapter: "standard-webhooks" | "course-hmac") → 401 if bad dedupe(id, KV, ttl) → 200 "duplicate" enqueue({ kind, body }) → 202 at once queue(batch) handler(job) ok → ack throws → retry(delay) push(target, msg) 2xx → event row "notified" else → retry, row stays pending

The per-lesson parts stay in each Worker: the handler, the policy, holds and owner codes, and the may lists.
